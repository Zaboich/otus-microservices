# Последовательный план демонстрации Service и Ingress

Демонстрация проходит на одном приложении: сначала обращаемся непосредственно к Pod, затем создаём Service, проверяем DNS и открываем доступ с хостовой машины через LoadBalancer и Ingress.

## 1. Подготовить стенд

До начала показа запустить Minikube, проверить подключение `kubectl` к учебному кластеру и подготовить два терминала и браузер. Один терминал использовать для команд, второй — для работающего процесса `minikube tunnel`.

Подготовить в одной рабочей директории четыре манифеста:

| Файл | Содержимое |
| --- | --- |
| `deployment.yaml` | Deployment `kuber`, namespace `default`, пять реплик, метка Pod `app: kuber` |
| `service.yaml` | Service `kuber-service`, тип ClusterIP, селектор `app: kuber`, порт `80` → `8000` |
| `loadbalancer.yaml` | Service `kuber-svc`, тип LoadBalancer, селектор `app: kuber`, порт `80` → `8000` |
| `ingress.yaml` | Ingress с правилом `/health`, `pathType: Prefix`, backend `kuber-service:80`, без поля `host` |

Все объекты приложения разместить в `default`. Приложение должно слушать порт `8000`, отвечать на `/` и `/health` и возвращать hostname Pod, чтобы можно было увидеть балансировку. В контейнере, из которого выполняются запросы, должны быть `sh` и `curl`.

В существующем `deployment.yaml` заменить образ `your-registry/kuber:1.0` на доступный образ приложения и установить `replicas: 5`. Проверить совпадение меток Pod и селекторов обоих Service. Для Ingress заранее проверить выбор контроллера и доступ с хоста с учётом ОС и драйвера Minikube.

Команды ниже выполняются из директории с подготовленными манифестами. Значения `<pod-name>`, `<pod-ip>`, `<service-ip>` и другие обозначения в угловых скобках нужно заменять фактическими именами и адресами из вывода команд. Команды `curl` внутри блока после `kubectl exec` или `minikube ssh` выполняются в открытой оболочке; `exit` возвращает в терминал хоста.

## 2. Запустить приложение и обратиться непосредственно к Pod

Показать Deployment: пять одинаковых реплик приложения, метка `app: kuber`, порт контейнера `8000`. Применить манифест и дождаться готовности:

```sh
kubectl apply -f deployment.yaml
kubectl rollout status deployment/kuber -n default
kubectl get pods -n default -l app=kuber -o wide
```

Обратить внимание на разные имена и IP-адреса Pod. Выбрать один Pod для выполнения запросов и IP другого Pod как адрес назначения:

```sh
kubectl exec -n default -it <pod-name> -- sh
curl http://<pod-ip>:8000
exit
```

Повторить запрос из оболочки ноды:

```sh
minikube ssh
curl http://<pod-ip>:8000
exit
```

**Результат:** приложение отвечает приветствием и hostname выбранного Pod. Для обращения приходится знать его IP и порт `8000`.

Пояснить, что при пересоздании Pod его IP может измениться. При нескольких репликах клиенту также пришлось бы самостоятельно выбирать экземпляр приложения. Следующий шаг — создать общую точку доступа.

## 3. Создать ClusterIP Service и показать балансировку

Открыть `service.yaml` и показать три настройки: селектор `app: kuber`, порт Service `80` и порт приложения `targetPort: 8000`. Объяснить, что селектор выбирает Pod с подходящей меткой в namespace Service.

```sh
kubectl apply -f service.yaml
kubectl get svc kuber-service -n default
```

Скопировать `CLUSTER-IP` созданного Service. Из оболочки Pod несколько раз обратиться к этому адресу:

```sh
kubectl exec -n default -it <pod-name> -- sh
curl http://<service-ip>
curl http://<service-ip>
curl http://<service-ip>
exit
```

**Результат:** один адрес позволяет обращаться ко всем репликам; среди ответов появляются разные hostname. Если первые ответы пришли от одного Pod, выполнить ещё несколько запросов. Строгое чередование реплик не требуется.

Пояснить разницу портов: клиент обращается на `80`, а приложение получает запрос на `8000`. Service задаёт стабильную точку доступа к группе Pod; отдельный Pod с reverse proxy для него не создаётся.

## 4. Проверить доступ по DNS-имени и показать настройки DNS

Открыть оболочку Pod и заменить IP Service его именем:

```sh
kubectl exec -n default -it <pod-name> -- sh
curl http://kuber-service
curl http://kuber-service.default
curl http://kuber-service.default.svc.cluster.local
cat /etc/resolv.conf
exit
```

Полное имя с `cluster.local` использовать при таком домене учебного кластера. Объяснить состав имени: Service `kuber-service`, namespace `default`, зона `svc`, домен кластера `cluster.local`.

Показать CoreDNS и Service, через который к нему обращаются Pod:

```sh
kubectl get pods -n kube-system -o wide
kubectl get svc kube-dns -n kube-system
```

Сопоставить `nameserver` из `/etc/resolv.conf` с `CLUSTER-IP` сервиса `kube-dns`. Для стенда со стандартной конфигурацией DNS Minikube эти адреса совпадают.

**Результат:** приложение доступно по имени без указания IP. DNS разрешает имя ClusterIP Service в его адрес, после чего запрос проходит к одной из реплик. Короткое имя используется в том же namespace, имя с namespace явно указывает расположение Service.

## 5. Открыть доступ с хоста через LoadBalancer

Показать `loadbalancer.yaml`: он выбирает те же Pod и использует те же порты, но имеет имя `kuber-svc` и тип `LoadBalancer`.

```sh
kubectl apply -f loadbalancer.yaml
kubectl get svc -n default
```

Показать, что у приложения теперь два Service. Обратить внимание на `CLUSTER-IP` и `EXTERNAL-IP`. Если внешняя интеграция ещё не предоставила адрес, `EXTERNAL-IP` будет находиться в состоянии `pending`.

Во втором терминале запустить туннель и оставить его работающим:

```sh
minikube tunnel
```

В основном терминале повторно проверить адрес:

```sh
kubectl get svc kuber-svc -n default
```

Открыть в браузере хостовой машины `http://<external-ip>` и несколько раз обновить страницу.

**Результат:** приложение доступно с хоста; hostname в ответах позволяет увидеть разные реплики. Пояснить, что LoadBalancer добавил внешний вход к приложению, а туннель обеспечивает доступ в подготовленном окружении Minikube.

## 6. Подготовить Ingress Controller и правило маршрутизации

Перейти к доступу через общий HTTP-вход. Остановить туннель во втором терминале сочетанием `Ctrl+C`, затем удалить Service `kuber-svc`:

```sh
kubectl delete svc kuber-svc -n default
kubectl get svc kuber-service -n default
```

Показать, что `kuber-service` остаётся: он будет backend для Ingress.

Включить Ingress Controller и дождаться его готовности:

```sh
minikube addons enable ingress
kubectl get pods -A
```

Найти Pod контроллера и убедиться, что он находится в состоянии `Running`, а его контейнеры готовы. Пояснить, что контроллер принимает HTTP-запросы и выполняет правила объектов Ingress.

Открыть `ingress.yaml` и последовательно показать настройки:

- Поле `host` отсутствует: запросы можно отправлять по IP без настройки доменного имени.
- Путь `/health` определяет, какие запросы будут направлены приложению.
- `pathType: Prefix` допускает совпадение по префиксу пути с учётом его сегментов.
- Backend `kuber-service:80` ссылается на порт Service.

Применить правило:

```sh
kubectl apply -f ingress.yaml
kubectl get ingress -n default
```

**Результат:** в кластере работает контроллер и создан Ingress, который направляет запросы `/health` к приложению.

## 7. Проверить доступ через Ingress

Использовать заранее проверенный для стенда способ доступа к контроллеру. Если требуется туннель, запустить `minikube tunnel` во втором терминале и оставить его работающим. В основном терминале посмотреть адрес Ingress:

```sh
kubectl get ingress -n default
```

Открыть в браузере `http://<ingress-address>/`.

**Результат:** контроллер возвращает `404 Not Found`, поскольку правило для корневого пути отсутствует. Пояснить, что контроллер уже доступен, но запрошенный URL не соответствует настроенному маршруту.

Затем открыть `http://<ingress-address>/health`.

**Результат:** запрос достигает приложения. Несколько раз обновить страницу и обратить внимание на hostname в ответах.

Для проверки `Prefix` открыть `http://<ingress-address>/health/extra`. Такой путь также соответствует правилу и передаётся backend; ответ на него зависит от приложения. Если приложение не поддерживает этот путь, заранее подготовить просмотр его логов, чтобы показать получение запроса. Сравнить с `/healthcheck`: этот путь не совпадает с префиксом `/health` по сегментам.

Пояснить, что при `pathType: Exact` правилу соответствовал бы только путь `/health`.

В завершение показать созданные ресурсы:

```sh
kubectl get deployment,pods,svc,ingress -n default
```

На экране остаются Deployment с репликами, ClusterIP Service `kuber-service` и Ingress. Проговорить логическую цепочку обработки запроса: клиент → Ingress Controller → backend Service → Pod приложения. Контроллер выбирает backend по HTTP-пути, а Service связывает его с репликами приложения.
